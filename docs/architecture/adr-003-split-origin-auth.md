# ADR-003: split-origin authentication and the external-access flow

Status: **Accepted — critic-60 and security-40 GO on joint design `4466b165` (2026-10-10). Implementation checkpoints require separate review.**
Date: 2026-10-10. Owner: access-codex. Tasks: T-0032 and the access backend supporting T-0033.
Inputs: [split-deploy brief](../briefs/split-deploy-auth-1.md), [access onboarding brief](../briefs/onboarding-access-1.md), [ADR-002](adr-002-multi-user-rbac.md).
Inspection baseline: `310f64ef`. This document defines the target contract, not current functionality.

## 1. Decision and compatibility

Keep a static frontend and all authority/state on the agent host's backend. Add optional split-origin mode, opaque short-lived human access tokens, rotating refresh families, and opaque one-use SSE tickets. All transports resolve ADR-002's stable users and live policy. Use a shared access planning/probing/publishing service for setup and Settings; the frontend renders its typed results and cannot grant permissions or apply host changes itself.

Same-origin cookie mode remains the default. Existing `taco_sess` cookies, HMAC secret, session expiry and revocations remain valid through ADR-002's migration; no forced logout and no surprise cross-site cookie mode. Same-origin installations may opt into the human token API. Enabling split mode permits human bearer requests on both API versions; it does not silently convert a cross-origin cookie into a human principal. Existing agent bearer tokens remain a different credential class with the same scopes.

Opaque access tokens are chosen over JWT because every request must consult live generations/roles anyway, the backend is one authoritative store, and immediate family revocation is required. This avoids a new signing-key/distributed-validation contract. The browser receives a random capability, not readable claims; its server-side record contains all required claims.

## 2. Shared claims, storage and gate order

The token migrations follow deployed auto-add migration 023 and RBAC migration 024; token-family schema is migration 026, after provenance migration 025. Migration numbers follow the PM's deploy-order assignment.

| Table | Essential state |
| --- | --- |
| `auth_families` | ID, user FK, origin, auth_generation, created/authenticated/last-used timestamps, idle and absolute deadlines, revoked_at/reason; optional linked cookie sid |
| `human_access_tokens` | Unique digest, family FK, user FK, session ID, audience, issued/expires timestamps, auth_generation, role_id/revision, permission_revision, registry_revision, revoked_at |
| `refresh_tokens` | Unique digest, family FK, parent/successor token IDs, created/expires, consumed_at; never plaintext |
| `stream_tickets` | Unique digest, user/family or cookie-session reference, origin, audience, fixed topic list, generation/revision fingerprint, created/expires/consumed timestamps |
| `auth_bootstrap_challenges` | Digested one-use CSRF nonce, purpose, origin, optional family binding, expiry/consumption; bounded and pruned |
| `audit_log` extension | Nullable validated origin; null means absent/non-browser, never the string "null" or unchecked header |

Generate 32 random bytes for each credential, with distinct human access (`ao_at_`), refresh (`ao_rt_`), ticket (`ao_st_`) and bootstrap prefixes; store SHA-256 digests. Existing machine tokens are not re-prefixed or rewritten. Unknown prefixed human credentials fail as human credentials, never fall back to the agent gate or a cookie. All responses/requests involving credentials are no-store; logs strip Authorization, Cookie, Set-Cookie, credential fields and ticket query values before serialization.

Audience is the persisted installation ID plus canonical public API base URL (including deployment prefix), not a request-controlled Host. Gate checks lookup, purpose/audience, expiry, active user, user auth generation, family activity/deadlines, role ID/revision, user permission revision and registry revision, then route RBAC. A stale permission fingerprint returns 401 `access-stale`; refresh issues a token against current policy. Invalid/unknown/expired/revoked credentials return generic 401. No stale token is allowed to retain old privileges until its time expiry.

Registry extension never widens non-admin authority (ADR-002 §2–§4, critic-57). Every new child starts at none for editor/reader/custom roles even if the existing role or user override grants parent write. Parent inheritance is legal only through an explicit stored role row naming that child; registering a different child grants nothing. Refreshing after registry_revision changes produces a current fingerprint, **not a grant**: the new action remains denied until an audited role edit or explicit user-child override authorizes it. Ticket issuance, command dispatch and stream delivery use the same rule.

Order: trusted-proxy normalization/security headers → bounded Origin/CORS/preflight handling → credential dispatch and request admission → JSON/media/CSRF checks → body-dependent machine scopes → route policy/read-only/capability gates → command recheck → handler. Audit captures the resolved principal even for refusals. If Authorization is present, cookies cannot supply additional authority. Malformed bearer never falls back. HTTP route metadata identifies whether human, agent, setup or public principals are legal. Human tokens bypass only cookie CSRF, not media validation, rate limits, explicit browser-origin refusal, RBAC or sensitive confirmation.

Access lifetime defaults to 10 minutes (configurable 5–15). Refresh family defaults to 12-hour idle and seven-day absolute expiry; rotation updates idle expiry but cannot extend absolute expiry. Config bounds are server-validated and visible in the access security summary. DB pruning preserves consumed refresh digests until their family absolute deadline so reuse remains detectable. Per-user generation revokes all credentials/session types; family revocation revokes its access tokens/tickets/streams immediately. Role revisions change authorization without increasing another user's credential generation.

## 3. Refresh cookie and the concrete authentication protocol

Two brief constraints need a concrete reconciliation. `__Host-` requires Path=/, which conflicts with endpoint-only scoping. Also a cross-origin login response cannot establish a cookie when fetched without credentials. Use a host-only `__Secure-ao_refresh` cookie (no Domain) scoped to the **externally visible** `<apiBase>/api/auth/refresh`, with HttpOnly, Secure, SameSite=None and explicit expiry. Reject duplicate refresh-cookie names; the API hostname and any same-site subdomains are deployment trust boundaries. Path is send scoping, not a substitute for authentication. These cookie/Fetch requirements are described by [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).

Keep every credentialed cross-origin fetch on the same refresh endpoint. Token-mode login and logout use operations there; legacy `/api/login` and `/api/logout` keep their cookie behavior. All refresh-endpoint operations require an exact allowed Origin, JSON, no redirects, the bounded auth parser, and rate admission before work.

| Endpoint / operation | Request and result |
| --- | --- |
| `POST /api/auth/refresh`, `operation: challenge` | `credentials: include`, `X-AO-Request: 1`, no mutation/session creation. Returns `{csrfToken, expiresAt, purpose}`; purpose is login/refresh/logout. Valid refresh cookie binds challenge to its family; absent cookie allows only login. Origin/custom-header checks protect this deliberately CSRF-token-free bootstrap operation. Nonce TTL two minutes, single use. |
| Same endpoint, `operation: login` | `{email, password}`, `X-AO-CSRF` login challenge; verify shared-throttled credentials/recheck user, create family and refresh token transactionally, Set-Cookie, return `{accessToken, expiresAt, me}`. Cookie admission is confirmed by a subsequent challenge before UI reports a persistent sign-in. |
| Same endpoint, `operation: refresh` | Current cookie plus family-bound one-use CSRF challenge; atomically consume old token and create successor/access token. Set successor cookie, return access token and fresh me/revision. |
| Same endpoint, `operation: logout` | Family-bound challenge; revoke family and linked cookie sid, clear refresh cookie using identical Path/Secure/SameSite/Partitioned attributes, close streams. Idempotent if already logged out; no private family metadata in response. |
| `POST /api/auth/logout-everywhere` | Human bearer or same-origin cookie, self declaration, recent confirmation; increment target generation and revoke all that user's families/cookies/tickets/confirmations. Then call refresh logout to clear browser cookie. |
| `POST /api/auth/reauth` | Human bearer or cookie, own password, shared throttle; confirmation bound to user/session/family/generation for five monotonic minutes. No arbitrary userId parameter. |

Challenges contain no token and are returned only to the allowed Origin with matching purpose. For refresh/logout, recheck the challenge against the presented cookie's actual family and digest at use, not merely an Origin. Expiry/consumption and rotation are in the same transaction. Challenge issuance does not consume/rotate refresh tokens and does not reveal whether an email exists. A token-mode login also revokes any existing refresh family presented in that browser partition; it never overwrites another user's family without revoking the old one.

Within the validated Origin/purpose/family boundary, inspect whether the presented refresh digest was consumed **before rejecting a previously consumed challenge**. A recognized replay carrying its still-valid bound challenge revokes the family even when that challenge was consumed by the original request; this detection path can never issue a successor. Otherwise an identical HTTP replay would be rejected as CSRF while leaving the stolen token's successor live. A missing/invalid/expired challenge cannot rotate or authorize logout. Tests cover both exact request replay and replay with a freshly obtained family challenge. Token-mode login rotates the browser's presented credentials; any valid same-origin taco_sess for the same user is revoked and replaced/linked explicitly, while unrelated users' sessions remain untouched.

On replay of any consumed refresh token, revoke the **whole family**, including successor access/tickets/streams, then return generic 401 and expire the presented cookie. Preserve transactional replay detection even if a connection drops after a successful rotation. No acceptance grace window or plaintext successor cache. Duplicate refresh requests therefore force reauthentication; frontend refresh is single-flight, retries are disabled, and tabs coordinate refresh/challenge/response delivery with Web Locks plus a same-origin BroadcastChannel (volatile messages, no durable tokens). Where Web Locks are unavailable, designate a tab leader; a lost leader causes reauthentication rather than concurrent rotation. An ambiguous network result requires login; automatic replay would revoke the family by design. Rotation/reuse detection follows the rationale in [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

The bearer/access token and CSRF challenges stay in browser memory only. No localStorage, sessionStorage, IndexedDB, service-worker caches, URL or downloadable config contains them. Reload obtains a challenge and rotates via the HttpOnly cookie. Draft/password/DNS token fields remain volatile and are cleared after use. Existing UI preference storage stays presentation-only.

## 4. Cross-site browser support is an explicit deployment result

Different origins can still be the same site: `office.example.org` on Vercel/GCS and `api.example.org` on the agent host is the preferred durable deployment. A `*.vercel.app` UI and unrelated API host is cross-site; browser policy may block an ordinary SameSite=None cookie. Support an explicit partitioned-refresh cookie option for cross-site deployment, using Secure/HttpOnly/SameSite=None/Partitioned and binding families to the UI origin. Partitioning is described by [MDN CHIPS](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies/Partitioned_cookies).

Probe actual cookie admission and rotation in the user's browser; never assume CORS success proves cookies work. If neither ordinary nor partitioned cookie works, show `blocked / browser-cookie-policy`, with a custom-domain or same-origin proxy fix. There is no universally available persistent cross-site cookie guarantee and no fallback to a browser-readable durable refresh token. Login access may work temporarily in memory, but the flow must not report full readiness. Reviewers/PM must accept this deployment limitation explicitly; changing it would require a different architecture such as a hosting-side auth proxy, contrary to the static-only target.

## 5. Origins, CORS, HTTPS and headers

`AO_ALLOWED_ORIGINS` is a JSON array of canonical HTTPS origins. Validate with WHATWG URL; forbid credentials, wildcard, null, fragment, query, any path other than `/`, non-HTTPS, duplicate origins and more than 16 entries. Normalize hostname case/IDNA/default port; comparisons use the exact resulting origin, including a non-default port. A trailing slash may normalize away. No suffix match, regex, public-suffix wildcard, request Host inference or reflection of arbitrary headers. Production public UI/API URLs must use HTTPS; local same-origin development remains unchanged. The instance file `access.allowedOrigins` maps to the same effective setting; env imposes an uneditable value that the UI explains.

Allowlisted browser Origin is required for refresh and ticket use and is checked on all split-mode browser requests, even bearer ones. Missing Origin may be accepted for ordinary non-browser bearer API clients; refresh/challenge always require it. Origin is a browser policy boundary, not proof against non-browser clients that can forge it; possession of a valid credential and RBAC remain required. No Referer/custom-header fallback substitutes for Origin on refresh. Removing an origin revokes its families/tickets/streams, invalidates challenges and updates the CORS gate immediately after successful config activation.

CORS supplies the exact allowed origin, `Vary: Origin` (and request-method/headers on preflights), explicit route-supported methods, headers `Authorization`, `Content-Type`, `X-AO-CSRF`, `X-AO-Request`, and approved protocol headers such as Last-Event-ID. Expose only X-Request-Id/Retry-After and required contract headers. Preflight max-age is 300 seconds; actual requests always recheck the live allowlist. **Allow-Credentials:true only for the refresh endpoint**. Ordinary bearer calls and EventSource use credentials:omit/withCredentials:false. Forbidden preflights fail before bodies, with no allow headers. Never use `*`, including for public diagnostic routes. OPTIONS runs without requiring bearer or evaluating a user permission, but only advertises a declared route.

Split-mode boot rejects missing HTTPS public API URL and insecure UI origins. Requests must arrive with a verified secure public scheme: bind backend to loopback/private network and accept forwarded scheme/host only from configured trusted proxy addresses; refuse attempts to reach it directly insecurely. Browser requests never follow auth/API redirects to another origin. API sends no-store for private responses, nosniff, Referrer-Policy:no-referrer and HSTS `max-age=31536000` on secure public requests (no includeSubDomains/preload default). API frame policy denies embedding. Static host sends strict CSP with exact API connect-src, object-src none, base-uri restricted, no inline-script relaxation, and equivalent referrer/security headers. HTTP→HTTPS redirection belongs at the public proxy, not an API response containing credentials.

Login/password/invitation/refresh share one IP/global throttle and expensive-work admission; add per-user request and refresh buckets plus existing stream session/global bounds. Defaults: API 300/minute/user and 600/minute/IP; refresh/challenge 30/minute/family and 60/minute/IP; access probes 12/minute/principal, at most two active jobs/principal and eight globally. Counts include refusals; bounded LRU state and Retry-After. Existing stricter agent-token limits remain. Resource-specific gateway restart cooldown/confirmation remains separate. Sensitive user/Settings writes use recent confirmation even if bearer authentication succeeded.

## 6. SSE ticket protocol

`POST /api/v[23]/stream/ticket` requires human bearer (or cookie in same-origin mode) and `{topics:[...]}`. Check each topic's current ADR-002 permissions, caps and origin; return `{ticket, expiresAt, streamUrl}` for a 30-second one-use ticket. Tickets contain no access token. Cross-origin caller uses `new EventSource(streamUrl, {withCredentials:false})`; URL is the fixed versioned stream path with only the ticket and, for reconnect, opaque resume identity.

GET stream consumes the digest transactionally before headers/stream creation. Require the exact family/cookie user/generation and permission fingerprint, audience and **actual Origin matching the issuing origin**, with the fixed topic set. Same-origin cookie streams still work without tickets. No stream may be resumed using just Last-Event-ID. On disconnect the client closes native EventSource, obtains a new ticket using its bearer, and reconnects; automatic retries with a consumed ticket fail. Resume additionally proves same session/family/user/origin and current revisions. New ticket explicitly pins the requested resume stream/sequence; previous replay admission cannot widen its topic set.

The stream lifetime is bounded by the authenticated access deadline (or existing cookie exp) and family validity. Before access expiry the frontend refreshes and opens a stream with a new ticket; it cannot stretch a 10-minute bearer into an indefinite stream. ADR-002 governs filtering/replay/queue revocation, including after role changes. Ticket leakage grants at most one admitted stream within 30 seconds under those restrictions, but remains credential leakage. Proxy/access/error/APM logs must redact its query; Referrer-Policy:no-referrer prevents propagation. No ticket appears in analytics, copyable links or audit. Capacity or handshake failure consumes the ticket; request a new one. Admission is rate-limited before streaming.

## 7. Threat model and residual risks

| Threat | Control and honest limit |
| --- | --- |
| XSS steals an access token / makes authorized calls | Volatile token, short lifetime, strict CSP/text rendering and safe links. XSS running inside the trusted UI can still act as the user and refresh via the browser; HttpOnly is not an XSS cure. |
| Refresh/login/logout CSRF | Exact Origin, CORS custom-header/JSON preflight, one-use purpose/family-bound CSRF challenges; no content-type/header bypass. Challenge operation is read-only and separately admitted. |
| Bearer theft/replay | TLS, no storage/log leakage, short expiry, live generation/revision and immediate family revoke. A stolen current bearer remains usable until expiry/revocation; Origin is not sender-constraining. |
| Refresh replay | Single transactional consume, preserved lineage/digests, family-wide revocation; lost response or duplicate tab call intentionally needs login. |
| Spoofed Origin/proxy headers | Origin is policy only; credentials/RBAC are authority. Trusted proxy CIDRs and public URL audience prevent forged forwarding/Host from defining trust. |
| Ticket leak/replay | 30-second single-use, bound origin/user/family/topics/revisions, log redaction and reauthorization at replay/flush. An attacker may still race the real browser if it obtains a ticket. |
| Old role, disabled account, mixed machine cookie | Current-state gate, immediate revisions/generation/family checks, typed credential dispatcher; no fallback or combined grants. |
| Access probe SSRF / DNS rebinding | Section 10's fixed resolvers, entered-target allowlist, public-address validation, pinned connection, no redirects, bounded operations and sanitized result categories. |
| DNS API token/external mutation | Write-only transient input, provider-fixed endpoint, constrained zone/record plan, confirmation, safe optional secret storage and explicit partial outcomes (section 11). |
| Compromised allowed frontend origin | It can use the browser's auth flow. Never allow an untrusted multi-tenant preview wildcard; remove/revoke an origin on compromise. |

OIDC later resolves `(issuer, subject)` to the same users through a credential-provider interface. It must validate issuer/audience/nonce/state and backend authorization-code PKCE before issuing these families; IdP roles cannot directly replace local RBAC. No OIDC implementation, claims trust or silent account linking by email is included now.

## 8. Shared setup/Settings access contract for chars-c

Only v3 gets the new endpoints. Existing v2 setup/network remains compatible and must use the same bounded probe implementation so its old arbitrary URL surface cannot bypass these controls. All endpoints use the current `{ok,data,...}` envelope and structured translated error categories; examples below describe the `data` payload. No HTML, upstream response body, raw OpenSSL/DNS errors or debug JSON is user-facing.

There is one access service with two namespaces: `/api/v3/setup/access` and `/api/v3/settings/access`. Setup requests are POST because they carry the existing `setupCode` in JSON; they require the open/recovery setup gate, its expiry/throttle and exact setup browser origin. An expired/locked gate invalidates every plan/job even after asynchronous work. Configured instances cannot use it. Settings read requires settings.network:read; planning/probing/writes require settings.network:write; publication and DNS writes additionally require recent self reauth and explicit confirmation. These endpoint exceptions/requirements are declared in ADR-002's route inventory. Neither code nor a plan ID becomes a general API bearer.

| Setup endpoint / Settings endpoint | Input and output |
| --- | --- |
| `POST /setup/access/state` / `GET /settings/access` | Setup body has only setupCode. Returns `AccessVM`: effective fields with source/editable/reason, supported modes/providers/proxies, runtime/saved revisions, defaults, last verification, restart requirement. No secret values. |
| `POST .../plan` | `{draft, settingsRevision}` (+setupCode); validate full draft, inspect safe local network/proxy metadata, return immutable `AccessPlan`. No DNS/config mutation. |
| `POST .../checks` | `{planId, checks:[dns|tls|cors|public]}`; start bounded job; return `{jobId, planId, state, pollAfterMs}`. No arbitrary hostname/URL/method/header in this request. |
| `POST .../checks/status` | `{jobId}`; returns typed observations, elapsed time and next-check delay, bound to requesting setup context or user/session. |
| `POST .../checks/cancel` | `{jobId}`; cancel pending sockets/timers; idempotent. |
| `POST .../dns/plan` | `{planId, provider:"cloudflare", apiToken, persistToken:false}`; validates token through fixed provider API, returns constrained `DnsChangePlan`; token is accepted once and held only for that plan's short lifetime. |
| `POST .../dns/apply` | `{dnsPlanId, expectedRevision, confirmation:{zoneId,recordIds,changesDigest}}`; consumes the plan and performs only the confirmed DNS changes. Returns explicit complete/partial/failed/unknown outcome. |
| `POST .../apply` | `{planId, settingsRevision, confirmation:{configDigest}}`; consume plan, recheck gate/policy/reauth/revision/env locks, publish Agent Office config atomically. Setup stages the access configuration in its draft; existing final `PUT /setup` publishes owner/runtime/access together. Settings publishes immediately with the existing safe publisher. |
| `POST .../verify` | `{planId}` or `{appliedRevision}`; recheck public DNS/TLS/API identity and return separate server/browser verification matrix. An old draft cannot be reported as active. |

`...` is exactly either namespace above. Plan/job IDs are random opaque identifiers, bound to principal/session, setup-code epoch or auth generation, origin, base config revision/digest, and boot ID. Plans expire after 15 minutes; DNS-token plans after five minutes. At most four plans/principal; failed/expired/cancelled plans erase transient credentials. Replanning invalidates old jobs/results. Checks may be retried explicitly within limits; no automatic DNS mutation or publication retry. Jobs and typed plan cache are ephemeral, bounded, and disappear on boot. Expensive external operations recheck authority both before dispatch and before storing results/committing. Job status does not leak another principal's plan existence (404).

The external-access state shape is named `ExternalAccessVM` to distinguish it from the existing agent-habilitations `AccessVM` (`GET /views/access`). `GET /settings/access` and `POST /setup/access/state` return this same shape. Setup responses are admitted only by the open setup code and report `state: "open"`; Settings requires `settings.network:read` and reports the configured state. Neither returns secrets.

`ExternalAccessVM` has exactly these top-level fields: `state` (`open|configured|readonly`), `settingsRevision` (global Settings revision or null in setup), `savedRevision` and `activeRevision` (access-profile revisions or null), `saved` and `active` (`{revision,draft}` or null), `draft` (`AccessDraft`), `fields` (source/editability/reason for `mode`, `apiPublicUrl`, `uiOrigins`, `domain`, `proxy`, and `security`), `choices` (`modes`, `proxies`, `dnsProviders`), `securityDefaults`, `securityHeaders`, `lastVerification`, `pendingActivation`, and `restartRequired`. Settings plan/apply use the global `settingsRevision`; it is never inferred from either access-profile revision. `saved` is what will apply on the next process start; `active` describes the effective runtime/security policy serving requests now. Persisted settings alone do not make a profile active: until the runtime and security transport expose an effective profile/revision, `active` remains the actual local/default policy and `pendingActivation` stays true for unsupported saved changes. Setup has null revisions and null saved/active values with a non-published draft. Settings publication may set savedRevision above activeRevision while the old active draft remains effective; pendingActivation is then true. `lastVerification` is `{revision,origin,checkedAt,expiresAt,state,checks,browser}` or null, and is valid only while unexpired and pinned to the active revision and declared origin. It never turns a saved-but-inactive revision into ready. `securityHeaders` is read-only policy metadata: the mandatory CSP, frame denial and HTTPS HSTS baseline are locked; only the exact HTTPS UI origin selected for split-origin may be added to `connect-src`. There is no user-authored header field in `AccessDraft`.

A DNS provider descriptor is `{id,labelKey,consoleUrl,nsSuffixes,nsPatterns,records,api}`; `records` lists supported `A|AAAA|CNAME` types and `api` is `none|plan-only|write`. The provider registry is shipped data, not a runtime-specific branch. Its public labels and instructions are keys resolved by the UI. Unknown is always present with `id: "unknown"`, no console URL, and `api: "none"`.

`POST .../plan` requires a complete `draft` and `settingsRevision` (the setup request also requires `setupCode`; its revision is null before the first saved config). `AccessDraft` is `{mode,apiPublicUrl,uiOrigins,domain,proxy,security}`. `mode` is one of the six values above; `apiPublicUrl` and every `uiOrigins[]` item are canonical HTTPS URLs/origins under §5; `domain` is a bare canonical DNS hostname or null; `proxy` is `caddy|traefik|cloudflare|manual`; `security` contains only the declared bounded token/refresh lifetimes and `partitionedCookie` boolean. Plan is read-only: it never resolves an arbitrary URL, calls an arbitrary endpoint, writes config, changes DNS, or applies a proxy recipe. Its `domains[]` entry is `{hostname,observedAt,provider,resolvers,records,proposals}`. `provider` is `{id,confidence,evidence}` where confidence is `high|medium|unknown`, and evidence contains only resolver IDs and matched NS names. `resolvers[]` is `{id,state,records}` with resolver ID `google|cloudflare`, state `answered|timeout|invalid-response`, and record groups `A|AAAA|CNAME|NS`; `records[]` items are `{name,type,value,ttl}`. A proposal is `{name,type,value,ttl,proxied,source}`; it is advice and is never applied by planning.

Plan `checks[]` entries use the `AccessCheck` shape below. `artifacts[]` is `{id,kind,filename,contentType,content}`; content is inert, bounded text with no secret or shell interpolation. `writes[]` is `{target,field,current,proposed,source,editable,requiresRestart}` and lists only the exact Agent Office config fields that a later apply would change. `externalActions[]` is `{kind,labelKey,required,state,details}` and records DNS/provider/proxy/hosting work that the operator must do outside Agent Office. Each `details` is a bounded map of display-safe strings and numbers. `environmentImposed[]` is `{field,source,reasonKey}` and explains locked environment values without revealing secret values. No absent or uncertain observation is rendered as a successful check.

`POST .../checks` starts only named checks already present in the plan. `checks/status` returns `{jobId,planId,state,elapsedMs,pollAfterMs,checks}`. Job and item states are `idle|running|waiting|passed|failed|blocked|unknown`; provider confidence is separate. Typed error `reason` and `fix` are `{key,params?}`, with `params` restricted to bounded strings/numbers. Public error keys include `domain.invalid`, `dns.timeout`, `dns.invalid-response`, `dns.resolver-disagreement`, `dns.no-delegation`, `dns.no-records`, `target.blocked-address`, `tls.certificate-invalid`, `cors.origin-not-allowed`, `check.cancelled`, `check.expired`, `check.capacity-limited`, and `config.environment-override`. DNS waiting is reserved for two valid, comparable observations that differ by name/type/value; TTL or record ordering alone is not divergence. Missing, invalid or empty evidence cannot pass. Raw DNS answers from a syntactically valid DNS inspection may include private addresses as evidence; any HTTP/TLS connection to a destination whose answers include a non-public address is blocked under §10.

The authoritative shapes and examples are `docs/architecture/examples/v3/external-access-vm.json`, `external-access-plan.json`, and `external-access-check-status.json`. DNS detection is read-only; writes require the separate plan/confirmation/apply routes above.

`AccessDraft` fields: `mode` (`local`, `lan`, `private`, `public-same-origin`, `public-split-origin`, `tunnel`), `apiPublicUrl` (`string|null`), `uiOrigins` (canonical HTTPS origin list), `domain` (bare canonical DNS hostname or null), `proxy` (`caddy`, `traefik`, `cloudflare`, `manual`), and `security` with bounded token/refresh lifetimes and partitioned-cookie choice. `local`, `lan`, and `private` drafts require null `apiPublicUrl`, null `domain`, and empty `uiOrigins`; they have no public DNS/TLS/CORS checks. `public-same-origin` and `tunnel` require a canonical HTTPS API base and a domain, with empty split-origin list. `public-split-origin` requires a canonical HTTPS API base, a domain, and 1–16 exact canonical HTTPS `uiOrigins`. All modes require a closed `security` object. Non-public modes retain the existing local/private listener policy and cannot supply a substitute target to a public probe. Tunnel hostname is explicit validated data, not an arbitrary redirect target.

`AccessPlan` includes `planId`, base revision/digest, `configDigest`, expiresAt, normalized draft, `domains` with provider confidence and DNS record proposals, typed checks, host proxy detection, artifacts, security summary, `writes`, `externalActions`, environment-imposed fields, and restart consequences. `configDigest` is lowercase SHA-256 hex of UTF-8 `JSON.stringify({version:1,baseRevision,access:draft})`, where `draft` is the validated normalized AccessDraft with fixed property order. It covers only the candidate persisted access settings, not DNS observations, artifacts or timestamps; clients treat it as opaque and echo it in apply confirmation. It states exact files/fields to change, never writes proxy/system/firewall files itself. Downloadable proxy/Vercel/GCS artifacts are inert text built from validated inputs (no newline/shell/config injection); they contain no credentials. Domain/record copying uses separate literal fields, not shell commands that interpolate untrusted input.

```ts
type AccessCheck = {
  kind: 'dns' | 'tls' | 'cors' | 'token' | 'refresh' | 'sse' | 'public';
  target: string; // validated domain/origin, never a credential URL
  perspective: 'server' | 'browser';
  state: 'idle' | 'running' | 'waiting' | 'passed' | 'failed' | 'blocked' | 'unknown';
  observedAt: number | null;
  elapsedMs: number;
  expiresAt: number | null;
  reason: { key: string; params?: Record<string, string | number> } | null;
  fix: { key: string; params?: Record<string, string | number> } | null;
  evidence: DnsEvidence | TlsEvidence | CorsEvidence | PublicEvidence | null;
  retryAfterMs: number | null;
};
```

DNS waiting means both resolvers returned valid observations and those observations have not converged to the proposal. A resolver timeout has no second observation to compare; it is `unknown` with `dns.timeout` (or a specific failed result), never propagation waiting. Show elapsed time plus resolver/record match counts, not a fabricated completion percentage. TLS passed means chain/hostname/time validation completed. CORS server passed means headers checked, not browser credential success. Browser cookie refusal is blocked with a concrete fix. Unknown proxy/provider/tunnel detection stays unknown and leaves manual choices available. No loading state implies success.

## 9. DNS provider data, recipes and browser verification

Provider detection lives in a reviewed JSON registry: stable ID, localized label/instruction keys, precise NS suffix patterns, console HTTPS URL and supported record/API capabilities. Initial entries: Cloudflare, Route 53, Google Cloud DNS, Namecheap, GoDaddy, OVH and Gandi plus unknown. Match a DNS label boundary on authoritative NS names, not a substring. Ambiguous delegations are unknown or a list of candidates with evidence; never an authority to send a token. Find the closest delegation by walking exact-owner NS answers from the entered hostname up at most three labels, using only the two fixed public resolvers and confirming the discovered owner at both. This uses live DNS delegation rather than a public-suffix database and never accepts arbitrary client-supplied resolver/query names. Provider instructions are copyable A/AAAA or CNAME records with separately typed name/value/TTL/proxy fields. A public IP is evidence with a source/time and can be unknown behind NAT; no guessed machine-private address becomes an Internet record.

Host inspection detects only known local metadata for installed Caddy/Traefik/tunnel tools without starting them or reading their secrets; unavailable access is unknown. Generate Caddy automatic-TLS, Traefik TLS and Cloudflare origin/tunnel recipes for exact domains/base prefixes; only the owner applies them outside the app. Backend TLS probes expose sanitized issuer, expiry, verified hostname and latency; absent/invalid certificate may have unknown metadata and a classified fix. Cloudflare frontend TLS success does not prove origin TLS; show that as a separate external action.

Server CORS checks send a fixed OPTIONS preflight for `POST /api/auth/access-diagnostic` with the chosen Origin and the declared `Authorization`, `Content-Type`, `X-AO-CSRF`, and `X-AO-Request` request headers. They validate exact ACAO, POST, required headers, and `Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers`; this public diagnostic route does not allow credentials. Credentialed CORS is checked only for the refresh endpoint. The probe also verifies the diagnostic response identifies this installation via a bounded nonce challenge. This is a **server perspective** simulation: a server setting an Origin header is not a browser test.

For real verification, chars-c's static client must run on the declared UI Origin and use the configured absolute API URL. After access publication, real login/challenge/refresh, bearer `/me`, ticket/SSE and forbidden-origin fixtures exercise the gate from the browser. A pre-apply draft or setup page opened on another origin reports browser checks `blocked / open-declared-ui` or `waiting / apply-required`, not passed. `verify` returns the server observations and a fresh five-minute diagnostic nonce; frontend displays its local browser observations separately, pinned to that nonce/config revision/origin. A browser report is advisory, cannot grant a permission, change config or bypass TLS. It is not treated as a trusted audit assertion. Final "Tout est prêt" requires current server checks plus locally observed browser authentication/refresh/SSE success on the declared origin; without a browser there is no end-to-end GO.

`POST /api/auth/access-diagnostic` is a narrowly public read-only endpoint with normal live allowlist/CORS: accept a bounded nonce and opaque plan ID and return installation ID, active access revision and nonce, never configuration/session data. A nonce is random, single-use, short-lived, and stored against the live plan/job plus the issuing session/setup epoch, auth generation, policy fingerprint, Origin and boot ID. The route consumes it only while that exact job/context remains current; probes require the exact nonce, installation ID and active revision in the response. It cannot mint user credentials or act on a candidate allowlist before apply. Authenticated checks use the actual human flow; there is no "probe admin token". Public setup remains code-gated and does not enable private API routes from a draft origin.

## 10. Probe SSRF and resource bounds

The probe service is an outbound boundary distinct from runtime adapter connections. Accept only entered DNS hostnames and validated configured API/UI targets captured in the plan. Internet probes use HTTPS port 443 only; diagnostic paths are generated from the normalized API prefix and a fixed allowlist (`/api/auth/access-diagnostic`, declared OPTIONS routes, `/healthz`, `/readyz`, `/build.json`). No arbitrary path, port, URL userinfo, query token, request headers, proxy, resolver, UNIX socket or protocol. Non-443 deployment origins may be valid CORS configuration but their public probe is blocked/unsupported, not silently probed. Local/LAN/private modes do not use a public fetch to inspect internal services.

Use two server-chosen public DNS-over-HTTPS resolver endpoints (Google Public DNS and Cloudflare) with fixed host/path/pinned resolver addresses and ordinary TLS verification; no system search domains or requester-chosen resolver URL. Query A and AAAA for the entered hostname; their answer sections carry and validate bounded CNAME chains (maximum four links). Walk NS owner names for at most three hostname ancestors on the first resolver, then recheck that exact owner with the second. This is at most eight total DNS queries per inspection; at most 16 records/type and 64 KiB decoded response. Apply three-second per-query and 15-second whole-job deadlines. No unbounded poll loop: client starts an explicit new bounded check after a suggested minimum five-second delay, respecting job/rate limits. Resolver disagreement is an observation, not permission to select a private answer.

Before any HTTP/TLS connect, classify **every** returned IPv4/IPv6 answer and reject a target if any is loopback/private/link-local/multicast/unspecified/reserved/documentation/benchmark/CGNAT or IPv4-mapped equivalent, including metadata addresses. Use an explicitly reviewed public-address classifier rather than a handful of regexes. Reject IP literal/decimal/hex/zone-ID hostnames, localhost and special-use names. Pin an approved resolved address through the HTTP agent lookup/connect path; preserve original Host/SNI and verify certificate chain/hostname/time. Do not resolve again in the socket layer, use environment HTTP proxies, pool across targets, disable TLS verification, or follow any redirects (including same-host redirects). Re-resolve/reclassify each new check to resist rebinding. A proxy to a private backend is permitted only as an owner-applied public infrastructure recipe, never as a probe target override.

HTTP has a five-second connect/TLS and ten-second total deadline within the job limit; stream-read at most 64 KiB, reject compression, stop oversized responses and cap headers/certificate fields. TLS errors return categories/fixes, not upstream bytes. Abort on cancellation, setup expiry or generation/revision changes. Retry at most one transient resolver failure, never a mutating request. Concurrency, job and rate caps from section 5 apply. Synthetic connectors override DNS/socket behavior only inside dependency-injected tests; there is no production "allow private probes" switch.

An entered-domain DNS lookup is allowed to report private/unexpected records, but fetching that destination is blocked. This distinction lets the UI explain the DNS problem without turning the setup/settings endpoints into a port scanner. Server verification cannot prove external reachability from every network or ownership of a hostname; TLS certificate/nonce checks and the operator's confirmed plan provide bounded evidence.

## 11. Cloudflare DNS adapter and publication boundaries

Provider adapters implement `detect`, `instructions`, `planChanges`, `applyChanges` and sanitized outcomes. Cloudflare is first; its network base is fixed `https://api.cloudflare.com/client/v4`, never supplied by the user or provider-detection JSON. The same TLS/address/redirect/size/time controls apply with a separate fixed-provider destination allowlist. API token is write-only JSON, capped length, and sent only in Authorization to that host; no shell/CLI use. Use least-privilege DNS-edit plus zone-read token restricted to the exact zone. Find the exact validated zone, and refuse unexpected account/zone/record scope. No bulk or cross-zone changes. Fetch no arbitrary pagination chain (bounded page/count).

DNS plan pins zone ID, existing record IDs and normalized before values, exact proposed records, target access-plan digest/revision and privilege context. Apply requires the owner to confirm those records, rechecks zone/current values and refuses drift, then performs only the pinned creates/updates. No deletion default, no mail/NS changes, no runtime/network restart. Token lives only in the five-minute pending plan and is erased after success/failure/cancel/expiry. Optional `persistToken:true` must be explicitly selected and included in the reviewed writes; put it only in existing private secrets publication, never the non-secret instance file. Future uses require new confirmation; API responses only show configured/not-configured.

External DNS calls cannot join a SQLite/filesystem transaction. Audit accepted intent before dispatch and sanitized per-record outcomes after; never say a failed config publication rolled DNS back. A network timeout after sending is `unknown`, forces reinspection/manual reconciliation, and is not automatically retried. Partial DNS success is `partial`, lists only safe record identifiers/results and allows a freshly planned reconciliation. Optional compensating changes require a new reviewed plan with current-value checks, not blind rollback. Persisting the optional token is a separate safe publication step; if it fails, DNS may still have changed and the token is erased.

Agent Office access config writes use `src/ops/config-publisher.js` and the existing private worker receipt/identity-aware rollback, expected revision/config digest, environment override guards and secret redaction. Fields: `access.mode`, api/UI public URLs, origins, cookie choice, bounded auth settings, and optionally provider credential reference in the secrets file. Do not rewrite an operator's env file: saved `access.allowedOrigins` supplies the default effective AO_ALLOWED_ORIGINS value; an explicit env override remains locked. Config validation version increments with backward-compatible upgrade and is documented before code.

For Settings, publish and commit before activation; rejected publication preserves live config/gate. After commit atomically activate CORS/auth policy, increment access revision, revoke removed-origin families/tickets and invalidate old verification/plans. Bind/network listener changes are staged until restart; expose both saved and active revision and pending-restart fields. API-base/audience changes revoke token families on activation, with an explicit review warning; existing same-origin cookies remain unless a security setting explicitly revokes them. A draft verification cannot overwrite active readiness.

Setup access apply stages a validated draft only; final existing setup publication commits owner/runtime/access together and consumes the setup code. Restart is offered through the existing explicit approval/revision/boot-pinned dashboard restart command, requiring settings.restart:write and recent confirmation, never invoked by access apply or by a probe. Proxy/DNS/tunnel steps outside Agent Office remain external actions. Never restart a runtime gateway as part of this flow. chars-c's footer/review must distinguish staged, published, pending restart and verified states and preserve one scrolling body at every size.

## 12. Deployment recipes and test/review gate

Implementation includes operator documentation for Caddy, Traefik and Cloudflare: TLS at public ingress, private backend binding, explicit trusted-proxy CIDRs, prefix-preserving cookie Path and routes, credential/ticket log redaction, no private-response CDN cache, SSE buffering off with appropriate timeouts, security headers, allowed origin examples, and origin TLS qualifications. Recommended domains: office.example.org and api.example.org; partitioned cross-site deployments require browser validation. Host config download is an artifact, not deployment.

Before coding, critic and security review **both ADRs together**, including the proposed refresh-operation endpoint, path-prefix choice, cross-site limitation, privileged users:write semantics and outbound-probe boundary. chars-c receives sections 8–11 for T-0033's storyboard; designer and owner approval precede that UI's implementation. UI/backend ownership is separate, but no endpoint behavior can be invented by the storyboard.

Required tests use synthetic resolvers/certificates/origins and temporary stores; no real network or real OpenClaw data. Migration, default seeding and role reset must not silently add inheritance/write rows.

Real-browser integration starts UI and API on two distinct HTTPS origins with a local trusted test CA, plus an unlisted third origin. Final implementation receives critic/security GO and designer GO for the storyboard/UI in addition to this design gate.
