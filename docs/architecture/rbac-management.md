# RBAC management HTTP contract

This contract implements ADR-002 in the internal guarded `mountV2` integration. The validated operator activation switch controls production registration. Management endpoints exist on `/api/v3`; they require a human identity. Machine credentials never fall back to a cookie.

All responses use the existing `{data,meta}` envelope and error format. Reads require `users:read`; writes require `users:write`, operational write availability, actual-user recent password confirmation, and the named confirmation below. Admin authority includes promotion to admin. Successful writes and typed permission changes are audited atomically by the repository; middleware audits refusals and failures without request bodies or tokens. A committed synchronous self-demotion/reset/revocation can return its accepted operation result even though it invalidates the caller's later requests.

| Method and path | Body fields besides confirmation/revision | Result |
| --- | --- | --- |
| GET `/users?offset=0&limit=50` | None | `{items:User[],nextOffset:number|null}` |
| GET `/users/:id` | None | `User` plus `overrides:[{resource,level}]`, `effective:{resource:level}` |
| GET `/roles?offset=0&limit=50` | None | `{items:Role[],nextOffset:number|null}` |
| GET `/permissions/resources` | None | `{revision,items:[{key,parent,namespace,labelKey,privileged:boolean|null,available:boolean}]}` |
| POST `/users/invitations` | `email,name,roleId` | `{token,expiresAt,user:User}` |
| POST `/users/:id/invitation` | None | Reissued invitation, invalidating the older link |
| PATCH `/users/:id` | One or more of `name,roleId,status` | `User` |
| PUT `/users/:id/overrides` | `permissions:[{resource,level}]` | User detail with the new overrides/effective matrix |
| POST `/users/:id/password-reset` | None | `{token,expiresAt,user:User}`; immediately revokes target credentials |
| POST `/users/:id/revoke-sessions` | None | `{revoked:true}` |
| DELETE `/users/:id` | None | `{deleted:true}`; Person/audit identity retained |
| POST `/roles` | `name,permissions` | `Role` |
| PUT `/roles/:id` | `permissions`, optional `name` | `Role` |
| DELETE `/roles/:id` | None | `{deleted:true}` |
| POST `/roles/:id/reset` | None | Known built-in default grants; future resources remain denied |

Write envelope data is `{ok:true,result:<table result>}`. Limits are 1–100; default 50. Lists reject unknown query parameters. Deleted users are omitted. `User` has `id,personId,email,name,avatarUrl,roleId,status,credentialSource,revision,lastSeenAt,createdAt`. Credential source is the non-secret enum `database|env|oidc`, so UI actions can explain immutable external accounts; hashes, generations and invitation digests are absent. `Role` has `id,slug,name,builtin:boolean,revision,permissions`. Role grants use `{resource,mode:'explicit',level:'none'|'read'|'write'}` or, only for a concrete declared child, `{resource,mode:'inherit-parent',level:null}`. Overrides are explicit levels. Unavailable resources remain visible as unavailable, with `privileged:null` when their descriptor is absent.

POST creations require `expectedRevision:0`. Every other mutation requires the target User/Role's current positive revision, not the global Settings revision. Stale revisions return 409. Admin role/overrides are immutable, env accounts cannot be reset/deleted/demoted, and disabling/deleting/demoting the last active admin returns 409 `last-active-admin`. Other protected-invariant failures use a fixed category in the normal error format.

## Current-user password and named action confirmation

In the internal guarded integration, POST `/settings/reauth` with `{password}` confirms the requesting user's actual credential. It shares login admission, returns `{ok:true,result:{expiresAt},revision:null,vm:null}`, and binds a monotonic five-minute proof to that user, session, generation and live permission fingerprint. The protected Settings VM's `reauth.expiresAt` describes only this session. Expiry/invalidation requires another confirmation; reauthentication does not authorize an action or replace a named confirmation. Keep the pending action and explain retry/expiry timing in the UI.

Every management write carries:

```json
{
  "expectedRevision": 1,
  "roleId": "rol_editor",
  "confirmation": {
    "action": "users.edit",
    "target": "usr_example",
    "name": "Camille",
    "revision": 1,
    "changes": { "roleId": "rol_editor" }
  }
}
```

`action` is the declared command: `users.invite`, `users.resendInvitation`, `users.edit`, `users.overrides`, `users.passwordReset`, `users.revokeSessions`, `users.delete`, `roles.create`, `roles.edit`, `roles.delete`, or `roles.reset`. Target is the stable target ID; invitation creation uses normalized email and role creation uses `new-role`. Name is the current target display name, or submitted creation name. Revision must exactly match `expectedRevision`. `changes` repeats exactly all submitted mutation fields except revision/confirmation, including concrete permission grants and chosen role/status. A boolean flag is insufficient, and changing the outer payload after confirming it is refused. Use `{}` for an action with no additional fields.

The UI must present the named target and requested changes before forming this confirmation. Invites and reset tokens are returned once, never stored in UI persistent storage/audit. Build invitation/reset links with tokens in a URL fragment. Current-user account/profile mutation semantics are specified below.

## Public credential-link acceptance

Opt-in whole-app wiring exposes POST `/api/auth/invitations/accept` and POST `/api/auth/password-reset/accept`. Both accept exactly `{token,password}` in JSON; no query parameters, account IDs, actors or authorization headers. The page reads the fragment into memory and strips it from history before submission. Password length is 12–1024 characters, the body limit is 4 KiB (including chunked requests), and compression is refused. Responses set `Cache-Control:no-store` and `Referrer-Policy:no-referrer`.

Admission reserves the same login IP/global/in-flight budget before CSRF or body parsing. Parser, media, readonly and invalid-link failures consume an attempt; 429 includes Retry-After. A request ends within 15 seconds; disconnect/timeout immediately prevents a later hash from committing. If hashing has started, its admission slot remains reserved until derivation settles, because native scrypt cannot be cancelled; early refusals release immediately. Hashing runs outside a transaction; link purpose/expiry/state/generation/issuing revision are rechecked inside one consume/password/audit transaction. Invalid, expired, reissued, revoked and used links return the same 400 `validation_failed` with `details:[{issue:'invalid-link'}]`. Strict-body and password errors use the normal fixed categories.

Success is `{data:{accepted:true},meta:...}`. It activates an invited database user or changes the active user's password, consumes the link once and increments credential generation. It never sets a cookie or logs the user in: present a completion state and direct them to sign in. Reset issuance already revoked prior credentials; accepting the reset revokes again. Audit failure rolls back consumption/password changes so a retry can succeed. Concurrent accepts produce one success. Public acceptance UI is delivered separately; operator activation mounts these endpoints.

## Current-user Settings mutations

In the internal guarded integration, legacy paths PUT `/api/v3/settings/owner` and POST `/api/v3/settings/password` mutate only the requesting human account. The Settings `owner` field remains for compatibility but describes that current user. It now includes `revision`; use this as `expectedRevision` for account writes, distinct from aggregate `SettingsVM.revision` used for installation configuration. The same value is available in `/me.permissionRevision.user`.

Profile body is `{expectedRevision,displayName?,email?}` with at least one actual change. Password body is `{expectedRevision,password}` with 12–1024 characters. Both require this user's recent password confirmation and a database-managed account; env/OIDC credentials are immutable and use the existing external-account reason. Unknown body fields, caller IDs/actors, stale revisions and reserved email collisions are refused. Accepted writes return `{ok:true,result:{updated:true,user:{id,personId,name,email,revision}},revision:<account revision>,vm:null}`. Re-fetch Settings afterwards; the returned acknowledgement never contains another user's data. Password/email changes increment the current user's generation and revoke its prior credentials/links; the refreshed taco_sess keeps its original expiry and session ID. Other users remain signed in. Confirmation invalidates and must be repeated for another sensitive action. Account mutations are database/audit transactions and do not rewrite installation config or historical-owner identity.

Remaining Settings configuration mutations use current declared authority and the same current-user monotonic confirmation where sensitive. Checks, detection and probes recheck immediately before deferred dispatch and after awaiting work. Integration plans carry only issuing user/session/generation/fingerprint metadata and config revision; another session or changed authority must make a fresh plan. Shared confirmation never enters the legacy owner-password path in the guarded integration. Deployment requires review of the operator activation and Settings consumer checkpoints.

## Queued project delivery

In the guarded backend, comments with agent mentions and summary regeneration retain verified acceptance metadata in the private delivery record. Before a new turn, including a turn resumed after restart, the worker checks the current user, Person, generation, accepting session expiry/revocation, and exact command grants. Metadata does not include the cookie, password or bearer token and does not appear in the thread VM. A legacy queued record without that binding fails closed and requires an explicit authorized retry. Existing tracking records represent previously dispatched agent work; tracking/reply/summary completion may continue after human access changes.

A pre-dispatch authority denial settles the public delivery as failed with reason permission-denied (existing sourceError.permission-denied translation), releases its summary lock and never automatically resends. Retrying a summary requires both the retry route's projects.comment:write and projects.regenerate:write; comment permission alone cannot retry that privileged action. A retry records the current accepting session/command and obtains a fresh summary turn identity.

Every new project agent turn requires current logs:read, flows:read and settings.runtimes:read in addition to its command grant, including summary regeneration and explicit retry. This rejects lower-authority turns from the shared upstream project session, which may retain privileged context from earlier work. A manual comment remains available; a mention without all three reads is saved with delivery unavailable and reason permission-denied. canMention is false for that reader. Each linked read and agent dispatch rechecks these permissions after awaits and inside runtime queues.

Migration 023 conservatively backfills historical agent comments with these three read requirements. New generated replies persist the same private provenance; HTTP and SSE filter their entire rows against the current reader, including after restart. Unknown, inactive or malformed provenance fails closed. Prompt construction applies the same filtering. Agent-derived history/system lines and pagination cursors are withheld without all related reads. Provenance and acceptance metadata are never VM fields. After an agent turn has been dispatched, tracking its accepted result remains background completion work; replies and summaries continue to obey current reader restrictions even when the accepting author loses access.

Mixed project discovery and importing its cached candidates also require logs:read, flows:read and settings.runtimes:read. A withheld reader receives an empty discovery view without scanning; import is refused before consuming private cached candidates. Human-triggered scans recheck current authority before each code-host owner and workspace git dispatch, after awaited results and before publishing the import cache. Background discovery retains its existing system scope.

Human-triggered cover regeneration requires all three project-context reads. Each queued automatic cover job from a human project mutation retains that mutation's live authority plus those reads; an ordinary project mutation remains valid even when its optional cover job is refused. Uploads require the project write grant. Jobs recheck before capability discovery, each gateway/CLI capability read, queued agent turns, each raster child process and file publication. Authorization refusal does not invoke a code fallback or automatic retry. Guarded background observers use local code rendering; they never start an unbound external image-agent turn. Previously accepted external image generation may finish, but lost authority prevents subsequent processing/publication.

Generated covers (agent or code) derive from project summary/context and require logs:read, flows:read and settings.runtimes:read for their URLs, board/detail thumbnails and image bytes. Known current manual uploads remain intentional project content. Unknown/orphan media is conservatively restricted like generated output. The shared HTTP/SSE projection clears inaccessible generated covers and uses the existing monogram fallback. Media checks run for GET, HEAD and conditional ETag responses; guarded media is private, no-store. Permission changes cannot erase content already received by a caller.

The internal createApp routeSecurity option composes complete-stack coverage before returning the app. Global login/logout/current-account, minimal health probes, credential links and frontend endpoints have closed declarations. Middleware that may terminate a request (parsing, CSRF, token admission, readonly refusals, errors, static files and fallbacks) has an explicit reviewed exception ID; no handler-name/arity inference grants an exception. Audit-router routes declare their instrumentation-only behavior before yielding to the real endpoint. Coverage recursively inspects actual mounted stacks, both API aliases, implicit HEAD and framework method-discovery OPTIONS. Explicit OPTIONS handlers need their own policy. Unknown middleware, undeclared routes, nonliteral middleware mounts and guards placed after terminating handlers fail coverage. Operator-enabled startup composes this coverage before listening.
The actual server enables this stack when the operator sets `auth: {"rbacEnabled": true}` in instance config or `AO_RBAC_ENABLED=1` in the environment. The optional file field is supported in config versions 1–3 and preserved by upgrades; environment `0` overrides the file. Invalid booleans/unknown auth fields or environment values other than `0`/`1` refuse startup. The default is disabled. `AO_RBAC_PREVIEW=1` remains restricted to `AO_ENV=test` for isolated integration fixtures. It binds the migrated database identity or stable env identity (only a domain-separated private HMAC change detector is persisted), enables independent database-user login, credential links, shared Settings authorization, both HTTP/SSE policy stacks and complete mounted coverage before listening. Setup mode uses the same coverage check without opening an identity store early. This is a startup switch; changing it requires restart. The management API and `taco_sess` name remain stable. Human split-origin token transport is not mounted by this switch. Deploying activation also requires the Settings account/config revision consumer checkpoint. Accepted legacy env cookies upgrade on authenticated responses without extending expiry; a sid-less cookie's digest becomes the upgraded SID so logout revokes both original and upgraded copies. Migration grace is persisted once from RBAC migration 024 time and cannot be extended by restart or lifetime changes.
Adapters may export `permissionResources`, an array of descriptors with `key`, `parent` (nullable), `labelKey` and `privileged`. Absence means no adapter-specific resources. Keys are confined to `adapter.<adapterId>.*`; invalid namespaces, duplicates, missing/cyclic/cross-namespace parents and changes to a persisted key's identity fail preparation before runtime creation/config publication. Guarded controllers validate and deduplicate enabled adapters deterministically at boot and on Settings changes. Preparing/canceling a runtime change never changes live permissions. Accepted apply synchronizes the complete registry, closes affected streams through registry notifications and preserves unavailable adapter grants as inactive; newly added keys grant nothing to non-admins. Returning an adapter restores only its previously explicit grants. Guarded boot defers the store's initial core-only sync until the selected adapter set is bound, so unchanged cold boots do not churn registry revisions. Existing adapters currently contribute no extra keys; core policy still governs their existing routes.


The Settings consumer distinguishes account and configuration revisions. It re-fetches Settings after a guarded account acknowledgement (`vm:null`) before submitting another account action. A profile-plus-password save may require a second password confirmation because the accepted profile changes the user's permission fingerprint. It must not replay the accepted profile. Legacy unguarded responses without `owner.revision` retain their existing owner/password body formats. Conflict keeps the local draft and offers an explicit confirmed reload; it never automatically overwrites a peer's accepted change. Independently withheld instance/network/restart groups remain null; the consumer displays no substitute editable fields and uses current Me permissions for configuration affordances. Self-account affordances remain independent of configuration grants.


Disabling the operator switch restores owner-only login and routes; it does not discard a persisted migrated identity. Cookie verification still resolves that identity and its credential generation, and refuses every non-owner session issued during multi-user mode. Existing owner sessions retain their expiry/SID and remain valid when credentials are unchanged. Environment credential changes continue to invalidate the owner's prior sessions after rollback. No rollback turns a reader cookie into owner authority.
