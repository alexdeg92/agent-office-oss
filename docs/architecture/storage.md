# Storage: the Agent Office store

Status: **contract 2.2** (2026-10-05; see the api.md changelog), plus S5 implementation notes (§2, §4, §5). Only the architect edits this file.

Agent Office needs its own durable state for:
- projects, sources, flags, history and people;
- office layouts and UI preferences;
- caches that are expensive to rebuild (Discord profiles, GitHub repo data);
- the quarantine counters and an audit log.

`~/.openclaw` stays **read-only**. The only exception remains the existing skill toggle, which goes through `openclaw config set`, never through a file write.

## 1. Choice: `node:sqlite`

- **Built into Node 24 (`DatabaseSync`):** no new dependency. `gateway.js` already uses it, read-only, for the device identity.
- **Synchronous API in a single process:** no connection pool, no async races. Every write is short (< 1 ms), so blocking the event loop is a non-issue at this scale.
- **Transactions:** a status move and its HistoryEvent commit together, and the "every change is in history" invariant holds even on a crash.
- **Rejected alternatives:**
  - JSON files: no transactions, and history would be rewritten whole on every append;
  - `better-sqlite3`: a native dependency, for no gain over `node:sqlite`;
  - an external database: one more service on the home server.
- **Experimental warning:** Node 24.21 (the installed version) no longer prints one for `node:sqlite`, so nothing is filtered. If a future Node prints it again, filter only `ExperimentalWarning` + `SQLite`; `--no-warnings` would hide every other warning.

## 2. Location and files

| Instance | Directory | File |
| --- | --- | --- |
| production | `~/.local/share/agent-office/` | `agent-office.sqlite` (+ `-wal`, `-shm`) |
| staging | `~/.local/share/agent-office-staging/` | same |
| dev | `~/.local/share/agent-office-dev/` | same |
| tests | `mkdtemp()` per test (`AO_ENV=test`) | same |

- **Instance (S5):** `AO_ENV` = `production` | `staging` | `dev` | `test`. If unset: `staging` when `PORTAL_READONLY=1`, `production` when `NODE_ENV=production`, else `dev`. The staging unit therefore needs no new variable.
- **Directory:** `AO_DATA_DIR`, defaulting to `$XDG_DATA_HOME` (or `~/.local/share`) plus the instance's directory name from the table. It's in `.env.example` and is not a secret.
- **Boot checks (S5; S6.2: R8-01), each refusing to start with a clear log line. Paths compare by filesystem identity (realpath, dangling symlinks followed); an existing store is inspected through an immutable read-only open BEFORE any mkdir/chmod/pragma/backup/migration, so a refused open leaves its files byte-for-byte unchanged:**
  - a non-production instance whose directory resolves to production's default;
  - `PORTAL_READONLY=1` together with `AO_ENV=production`;
  - a data dir whose `store_meta.instance` names another instance. A data dir belongs to one instance for life.
- **Permissions:** the directory is created `0700`, the files `0600`. Project data and Discord profiles are personal.
- **Backups:** `backups/agent-office-YYYYMMDD.sqlite` via `VACUUM INTO` a temporary file, then an atomic rename (S6.2, R8-05: a failed backup never removes the previous one), daily at 04:00 local time and before every migration. The last 7 daily backups and the last 3 pre-migration ones are kept.
- **Staging never shares prod's file.** A staging instance pointing at prod data would be a write path into production.

## 4. Schema

**Migrations:** `001_init` creates the core; `003_sessions` (S6, R1-09) adds `revoked_sessions (sid, expires_at)`, pruned daily once expired; `004_api_tokens` (S7d) adds `api_tokens (id, hash, agent_id, scope, created_at, revoked_at)` and the per-store `api_token_salt` (one row, generated by the migration; a hash is `sha256(salt ':' token)`, so a copied row is useless in another store); `002_projects` (pulled into S5 for projects-05) creates the project tables and the repo/workspace caches. Layout tables stay for S14b.

**Migration 001 (S5) creates only the core:** `store_meta`, `persons`, `ui_prefs`, `interlocutor_cache`, `quarantine` and `audit_log` (`src/store/migrations/001_init.sql` is the executable version). The other tables below get their own forward-only migrations when their contracts are final:
- the project tables (`projects`, `project_sources`, `project_flags`, `project_people`, `history_events`) in S15a, after the 2.1 merge of the projects proposals (`reorder` needs a rank column, for example);
- `repo_cache` in S15b;
- `office_layouts` and `office_layout_revisions` in S14b, after office-dev's R3-14 (layout identity and retention).

Creating them now would mean a corrective migration later. The DDL below remains the target.

**Migration 002 (S5, projects-05)** lands the project tables in a slightly different form from the DDL below (`src/store/migrations/002_projects.sql` is authoritative):
- each flag, source and event row keeps its key columns plus the **domain object as JSON** (`data_json`), validated with the projects module's own schemas on write and on read;
- `projects.summary_meta_json` replaces `summary_actor_json`/`summary_at`;
- `project_people` gains `added` (an added, not derived, person);
- `repo_cache` gains `authors_json` (author hints: name + email hash), and `last_attempt_at` is nullable;
- `workspace_snapshots (source_id, data_json)` is new;
- session-group snapshots are **not** stored: they're session data, rebuilt from the engine after a boot.

**Migration 016** adds nullable `projects.summary_turn`, internal pending summary identity. It restores active comment delivery identities already in `follow.summary.turnId`; legacy null retry identities are adopted transactionally on thread attach. Claim/release changes no public project revision, history or activity clock. Summary writes check the exact stored identity and revision in the repository transaction. Manual summary changes cancel that identity. Accepting a comment-driven summary inserts its delivery and claims the lock in one transaction; final settlement/release and delivery state commit together. The column is omitted from canonical project objects and public VMs.

The repository (`src/store/repos/projects.js`) runs the projects module's own repository logic over SQL-backed collections, one transaction per public method, so the rules exist once (`plan.*`) and a refused command writes nothing. It passes `test/projects/repository-contract.test.js` unchanged.

**S5 differences from the DDL below:**
- **`store_meta (key, value)`:** `instance` and `created_at`, for the instance guard (§2).
- **`interlocutor_cache.id`:** also accepts `discord-guild:<snowflake>` (guild names), and is CHECKed to the three `discord-*:<digits>` shapes. A failed lookup is stored as `resolution='failed'` with no profile.
- **Migration 007 `open_identities` (G3b, ADR-001 §12.5, planned there as "004"):** the `interlocutor_cache` CHECK widens to `<family>-(user|room):<opaque>` (family a ChannelRef slug, opaque 1–128 chars without control characters; ≤ 170 chars in all); Discord rows are kept byte-identical (`discord-channel:` stays the 2.x alias of `discord-room:`, `discord-guild:` stays). Profiles: Discord's snowflake schemas, else the generic `{displayName, avatarUrl}`. New table **`person_identities (person_id → persons ON DELETE CASCADE, family, external_id, created_at, PRIMARY KEY(family, external_id), UNIQUE(person_id, family))`**, filled from `persons.discord_user_id`; that column is no longer written or read (dropped in the 3.0 cleanup). `Person.links.discordUserId` reads the `discord` identity.
- **`persons_agent`:** indexed on `(agent_id, ifnull(subagent_id,''))`, so a NULL sub-agent can't be duplicated (NULLs are distinct in a plain UNIQUE index).
- **`quarantine`:** value-free since S4.1 (no `source`, `detail`, `schema_*`, `openclaw_version` or `sample_json`); `path` is CHECKed to start with `$`.
- **`audit_log.detail`:** CHECKed to a lowercase category (`GLOB '[a-z]*'`), never a message.

JSON columns are validated with the schema DSL on write **and** on read. A row that fails on read raises a `store.invalid` issue (engine.md §5) and is skipped, never returned half-parsed.

## 5. Access layer

```
src/store/
  db.js             open, pragmas, migrate(), backup(), close()
  migrations/001_init.sql, 002_….sql
  repos/projects.js history.js persons.js layouts.js prefs.js caches.js quarantine.js audit.js
  tx.js             withTx(fn) → BEGIN IMMEDIATE … COMMIT / ROLLBACK
```
- **Repositories return canonical types** (data-model.md), never rows.
- **Repositories are the only writers.** API commands, the risk monitor and project-activity ingestion all call the same methods (projects.md `REPOSITORY_METHODS`; the domain rules live in the projects module's `plan.*`, called inside `withTx`). For example, `projects.setStatus({id, expectedRevision, status, actor})` does the following in one transaction:
  1. check the revision, else throw `ConflictError` carrying the current revision; the API turns it into the 409 `current` payload;
  2. if nothing changes, stop: no-op, no write, no event;
  3. update `status`, `revision + 1` (once per transaction) and `last_activity_at` (meaningful kinds only, data-model §9.1);
  4. insert the history events listed for that command in api.md §5.4;
  5. append an audit row.
- **After each committed transaction,** the repository publishes one batch on the shared change bus (engine.md §8), for example `[{source:'store', type:'Project', op:'upsert', id}, {source:'store', type:'HistoryEvent', op:'upsert', id, projectId}]`. Nothing is published for a rollback or a no-op.
- **S5 implementation (`src/store/`):**
  - `db.js`: open, permissions, migrations, the boot guards, `backup()` and `withTx`;
  - `repos/`: `quarantine.js`, `caches.js` (interlocutors), `audit.js` and `persons.js`, the S5 repositories;
  - `index.js` (`openStore`): composes them, binds the engine and runs the daily maintenance.
- **Quarantine write-behind:** `quarantine.record()` marks issues dirty, and the store flushes them every 5 s and on SIGTERM/SIGINT. Restored issues are not re-sanitised: they were sanitised before they were written, and sanitising twice isn't idempotent.
- **Audit (S5; S6.2: R8-06/07):** matching is an Express Router declared with the same patterns as the real routes (same case-insensitive, trailing-slash semantics), so every variant that can execute is audited; the actor is the verified session's owner, else `{kind:'anonymous'}` (401s included). One middleware, mounted **before** the read-only backstop, covers the six legacy write routes and the v2 mute (`flows.{run,enable,disable,delete,create,edit}`, `chat.send`, `skills.setEnabled`, `gateway.restart`).
  - **Outcomes:**

    | Response | `outcome` | `detail` |
    | --- | --- | --- |
    | 2xx | `ok` | none |
    | 403 | `rejected` | `readonly` |
    | other 4xx | `rejected` | `http-<status>` |
    | 5xx | `failed` | `http-<status>` |
    | 2xx with `ok:false` | `failed` | `cli-not-ok` |

  - A 401 has no actor and isn't recorded.
  - `target` is the route's id segment; bodies and messages are never stored.
- **Ids:** `prefix + '_' + base32(crypto.randomBytes(10))`, which gives 16 sortable-enough chars. Ordering uses `at` and `id`, never the id alone.

### 5.1 Migrations
- **Format:** numbered SQL files, applied in order at boot inside one `BEGIN IMMEDIATE` each, recorded in `schema_migrations`.
- **Before migrating:** if the database exists and a migration is pending, take a pre-migration backup first.
- **Forward-only.** A bad migration is fixed with a new one; rollback means restoring the pre-migration backup (documented in the runbook).
- **Boot guard:** if the database has a `schema_migrations.version` higher than the code knows (a newer build ran before), the server refuses to start with a clear log line. It does not run against an unknown schema.

### 5.2 Seeding (first boot)
- Persons:
  - the owner (Owner), as `human`, `is_owner = 1`, named from `PORTAL_EMAIL`'s local part until edited (at boot);
  - each configured agent, as `agent`, the first time the gateway lists it (S5: on the engine's `change`).
- The default office layout (S14b, with its tables) from `design/office/layout.example.json`, validated against `layout.schema.json`'s rules.
- No projects. The board starts empty with *Nouveau projet*. Proposed projects from sources are a later, explicit action.

## 6. Staging and the read-only guard

Today `PORTAL_READONLY=1` blocks every non-GET route, because staging shares the real gateway and CLI. With the store, there are two kinds of writes:

| Write kind | Example | Staging |
| --- | --- | --- |
| OpenClaw mutation (CLI, gateway) | cron edit, skill toggle, gateway restart, chat turn | **always blocked** (`readonly` error) |
| Agent Office store only | move a project, save a layout, prefs | **allowed** when `PORTAL_READONLY_STORE=0`, since staging has its own data dir |

**Proposal:** keep `PORTAL_READONLY=1` meaning "no OpenClaw mutations", enforced in the CLI wrapper and the gateway-restart command (not only in an Express middleware), and add `PORTAL_READONLY_STORE` (default `1`). The PM can then flip it on staging to test Projets and the office editor for real. PM decision.

## 7. Retention and size
- `history_events`: kept forever. Rough estimate: 50 projects × 30 events a day ≈ 0.5 M rows a year, under 200 MB. Revisit if it grows.
- `audit_log`: 365 days, pruned daily.
- `quarantine`:
  - `resolved` rows older than 30 days are deleted;
  - `open` rows are kept; `muted` rows are deleted after the audit period (G8);
  - at most 500 fingerprints; beyond that, new fingerprints are counted under one `quarantine.overflow` row so a flood can't fill the disk.
- `office_layout_revisions`: the last 20 per layout.
- **Caches:**
  - `interlocutor_cache` refreshes resolved profiles after 7 days and retries failed lookups after 1 day;
  - entries still fresh are preloaded at boot, so there's no refetch storm after a restart;
  - `repo_cache` is replaced on each fetch.
- **Maintenance (S5; G8 policy in `operations.md` §3):** daily at 04:00 local time: the backup, audit pruning (365 days, `AO_AUDIT_RETENTION_DAYS`), and quarantine pruning (resolved issues 30 days after their last occurrence, `AO_ISSUE_RETENTION_DAYS`; **muted** issues after the audit period; open ones stay), in memory and in the store. It logs counts only.
- **Backup and restore (G8):** `agent-office backup | restore` (`operations.md` §2); a running server holds `<data>/.server-lock.sqlite`.

## 8. What is deliberately not stored
- **Sessions, transcripts, cron jobs, cron runs, skills, channels:** OpenClaw owns them. Agent Office only stores **references** (session keys and run ids in history payloads) and the derived HistoryEvents.
- **Secrets:** no plaintext passwords, runtime/session tokens or cookie contents. New onboarding intentionally stores the owner login email and scrypt hash in `users`; repository author hints still use `git_email_hash`. Every DB backup containing owner credentials is sensitive.
- **Login sessions:** they stay stateless HMAC cookies (`taco_sess`).

## Onboarding owners and recovery (migrations 014–015)

`users` stores stable id, Person foreign key, case-insensitive unique login email, scrypt hash, timestamps and the sole supported role `owner`. Migration 015 removes unimplemented admin/member roles, adds durable `setup_status`/`setup_config_hash` metadata, and permits the separate `agent` peer inventory role. DB-auth ownership is the users row's Person link; `persons.is_owner` remains a legacy bootstrap compatibility field, not another authority for DB login. DB cookies carry `userId`; env/file credentials continue to work independently.

An open setup draft amends the same users/person rows and seeds its layout in one SQLite transaction. Finalization stores the validated layout and planned config digest in a transaction, publishes private files, then sets `configured`. Boot reconciles a matching digest after a crash; a missing owner or mismatched open draft opens code-protected local recovery. A configured owner cannot be reset through setup. Missing private secrets serve locked setup with a restore-and-restart message; they never reopen setup writes or reset the owner.

This is an intentional exception to the former no-login-credentials-in-the-store boundary: the DB holds a password hash, never a plaintext password or runtime/session token. Private DB backups consequently include the owner hash even without `--include-secrets`; that flag includes the separate instance secrets needed for a complete restore. New onboarding saves `owner.authSource="database"` in config and keeps only the session signing secret and runtime token in `secrets.json`. The users repository is never projected directly into an API response.
